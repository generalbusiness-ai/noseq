Prioritized findings

[DESIGN-01] P1 — Reconcile MLS branch revision with the noseq interpretation contract.
Evidence: A §4 lines 155–160 requires atomic outcomes/frontier; §6 lines 208–221 chooses Marmot as the candidate; §7 lines 267–281 promises unchanged retries and predecessor-verified order. [A:155](https://github.com/generalbusiness-ai/noseq/blob/2554c582db730cd3d64490970a573eab1463672e/notes/2026-09-06-noseq-architecture.md#L155).
Primary evidence: pinned Marmot [convergence.md:31](https://github.com/marmot-protocol/marmot/blob/4a2bc65f8db5866cec3b2a127dedb37818eaf207/protocol-core/convergence.md#L31), lines 340–341, 387–390 and 409–413: Settled is local rather than final; branch choice excludes transport order; later selection can withdraw payloads and membership notifications. This is a protocol requirement, not merely a library scheduling detail.
Impact/scenario: clients apply an action after one membership Commit, then a late competing branch changes accepted membership and withdraws the payload. A folder that only advances its immutable entry cursor can retain an effect the cryptographic layer has withdrawn. The same retained noseq prefix must not acquire meaning from whichever unsequenced MLS inputs or timers a device happened to observe.
Fix sketch: specify the authoritative crypto-input set at each noseq prefix, membership boundary, deferred/losing-branch dispositions, and whether any application interpretation can revise. Prove the selected adapter with competing commits, late witnesses, reordering, restarts, and withdrawals. Do not silently replace Marmot's branch selector with sequencer arrival order. A single authorized group-change writer can bound the first experiment, but its competing/invalid-input behavior still needs an explicit contract.
Gate: stop encrypted-client integration if no compatible profile can preserve the chosen noseq semantics; changing those semantics is a new design decision.
Effort L; change risk HIGH because it affects ordering and membership; confidence HIGH in the gap, feasibility remains unproven.

[DESIGN-02] P1 — Specify an authenticated history archive and durable client crypto state.
Evidence: A §6 lines 215–221 leaves archive/history/snapshot policy open; §4 lines 155–160 distinguishes caches from cryptographic state; §10 lines 421–425 lists recovery cases. [A:215](https://github.com/generalbusiness-ai/noseq/blob/2554c582db730cd3d64490970a573eab1463672e/notes/2026-09-06-noseq-architecture.md#L215).
Primary evidence: Marmot [retained-history.md:79](https://github.com/marmot-protocol/marmot/blob/4a2bc65f8db5866cec3b2a127dedb37818eaf207/protocol-core/retained-history.md#L79) explicitly limits old payload processing despite retained transport objects; [durability.md:68](https://github.com/marmot-protocol/marmot/blob/4a2bc65f8db5866cec3b2a127dedb37818eaf207/protocol-core/durability.md#L68) requires unresolved publication and exact prior/pending state to survive interruption. RFC 9420 [§3.2 and §16.6](https://www.rfc-editor.org/rfc/rfc9420.html#section-3.2) explain why new members lack pre-join messages and erased secrets cannot restore them.
Impact/scenario: an offline participant returns after several epochs, or a fresh device has the signing key and every ciphertext but cannot recover old actions or provenance. Separately, a crash after decryption or outbound encryption advances the MLS ratchet but loses the recoverable action/obligation, so clearing a UI cache exposes an unrecoverable gap.
Fix sketch: choose one initial policy: encrypted archives of original authenticated actions and verification evidence, or an explicitly trusted snapshot with an authorized start boundary. Define exactly who may receive earlier history, archive coverage proofs, keys and rotation, and atomic/recoverable links between crypto state, decrypted-action retention, outcomes, frontier and pending sends. Key backup, application rebuild and MLS rejoin are separate procedures. Never claim full original replay from a snapshot or forward secrecy for data retained under a recoverable archive key.
Gate: archive restore and cache-deletion replay must work before onboarding is called complete.
Effort L; risk HIGH because retention changes confidentiality and recovery; confidence HIGH.

[DESIGN-03] P1 — Declare what happens to permanently unreadable sequenced entries.
Evidence: A §4 lines 155–158 pauses on missing decryption material/output errors; §7 lines 235–239 admits opaque bytes and validates inner content later; lines 272–275 distinguish application rejection from interpretation failure. [A:235](https://github.com/generalbusiness-ai/noseq/blob/2554c582db730cd3d64490970a573eab1463672e/notes/2026-09-06-noseq-architecture.md#L235).
Impact/scenario: an admitted participant submits correctly signed outer bytes that can never be decrypted or validated. The sequencer cannot detect this. Every subsequent application action can become permanently inaccessible behind that position; one device may instead appear merely to lack keys. A local “skip unreadable” decision would make clients disagree.
Fix sketch: define a small deterministic interpretation taxonomy: authenticated business rejection; cryptographic/protocol invalidity provable from the selected state; temporarily unavailable dependency; locally missing/corrupt secrets; runtime failure. Decide which can have a protocol-defined terminal disposition and which must stop. If the first prototype intentionally stops permanently on malicious opaque input, state that availability limitation and expose the blocked position; any recovery/reinitialization path must preserve provenance rather than manufacture an ineffective action.
Gate: negative fixtures must produce identical outcomes or identical explicit stop conditions on all authorized clients. This cannot be deferred merely as UI error handling.
Effort M; risk HIGH because a wrong skip rule corrupts meaning; confidence HIGH.

[DESIGN-04] P1 — Define the public transport-admission authority and its log boundary.
Evidence: A §7 lines 235–239 and 260 asks the opaque server to enforce submitter admission; §9 lines 345–365 supplies initial public configuration; §10 lines 408–412 gives application authority control over membership. No update path between those two authorities is specified. [A:260](https://github.com/generalbusiness-ai/noseq/blob/2554c582db730cd3d64490970a573eab1463672e/notes/2026-09-06-noseq-architecture.md#L260).
Impact/scenario: an encrypted removal takes effect for folders while the public allowlist still admits the old member, or service access is granted before the authorized MLS Add is effective. A hostile provider's ACL decision must not become application membership merely because the next entry has a valid sequencer signature.
Fix sketch: define a minimal, separately signed public control plane rooted in genesis: permitted admission controllers, grant/revoke subject, monotonic version or exact preceding control state, instance binding, expiry semantics, and when changes take effect relative to app submissions. Pin how encrypted application authorization validates the same change independently. Server admission grants transport access only; it never proves decryption authority. Define whether and how a revoked submitter may recover an already committed receipt without being allowed a new append.
Gate: grant/revoke races, stale grants, public/inner-author mismatch and revoked exact retries belong in the first protocol tests.
Effort L; risk HIGH due to cross-layer authorization; confidence HIGH.

[DESIGN-05] P1 — Make invitation redemption and device addition an explicit recoverable protocol.
Evidence: A §9 lines 351–365 gives reservation/genesis binding and invitations; §10 lines 385–425 promises a short joining flow but leaves online admission and recovery open; lines 427–430 notes key-copy revocation limitations. [A:408](https://github.com/generalbusiness-ai/noseq/blob/2554c582db730cd3d64490970a573eab1463672e/notes/2026-09-06-noseq-architecture.md#L408).
Impact/scenario: a user approves Join but receives service admission without a usable Welcome, or a repeated redemption consumes two grants/key packages. A substituted invitation routes the user into an attacker's valid but different genesis. Copying signing identity onto a second device does not safely clone or independently revoke an MLS leaf.
Fix sketch: use an online authorized inviter for the first profile and show pending approval/delivery states. Bind the inviter's signed invitation and redemption proof to genesis, recipient key or approved acceptance, nonce, expiry/use policy, requested rights and history policy. Persist idempotent transitions through application grant, public admission and encrypted Welcome; verify the Welcome's group and credential binding before activating the UI. Define device credentials, key-package use, concurrent browser-tab ownership and lost-device behavior even if general device revocation is deferred. If every device is lost and no qualifying backup exists, say unrecoverable rather than silently creating a new identity.
Gate: expired/reused/substituted invitation, offline inviter, crash between each transition, fresh-device restore and lost-all-devices scenarios.
Effort L; risk HIGH; confidence HIGH.

[DESIGN-06] P1 — Freeze the signed wire, actor-proof closure and three distinct retry identities.
Evidence: A §7 lines 241–270 lists conceptual fields and calls for a wire spike; §9 lines 345–349 leaves profile identities illustrative. [A:251](https://github.com/generalbusiness-ai/noseq/blob/2554c582db730cd3d64490970a573eab1463672e/notes/2026-09-06-noseq-architecture.md#L251).
Primary evidence: Marmot [application-messages.md:45](https://github.com/marmot-protocol/marmot/blob/4a2bc65f8db5866cec3b2a127dedb37818eaf207/foundation/application-messages.md#L45) forbids adding a top-level Nostr signature to its inner event; lines 70–72 bind inner identity to the authenticated MLS sender. Thus “make the rumor signed” is not an interoperable fix. NIP-59 also distinguishes an unsigned rumor from its proof envelope.
Impact/scenario: two clients sign different encodings of the same intended action; cross-instance replay succeeds because the domain is absent; re-encryption creates another application action; or an archive retains plaintext but loses the evidence that binds it to its author.
Fix sketch: publish versioned byte-level fixtures covering genesis, signed inner action structure carried in compliant app content, outer submission, sequencer entry, receipt and control updates. Pin parser behavior for duplicate keys, Unicode, integer range, unknown fields, tag ordering and size expansion. Distinguish logical action ID, exact encrypted submission ID and sequencer/relay event ID; define dedup scope and retention and rejection of reused IDs with changed bytes. Retain the complete original verification closure, including sender/account binding, while keeping archive assertions distinguishable from actor proof.
Gate: independent encoders/verifiers must agree byte-for-byte; mutated, cross-instance, stale-definition and signer-mismatch fixtures must fail predictably.
Effort L; risk HIGH due to wire permanence; confidence HIGH.

[DESIGN-07] P1 — Select a real group-readable relay profile and a bounded complete-prefix protocol.
Evidence: A §5 lines 169–181 leaves kinds/schemas open; §7 lines 277–281 separates freshness; §8 lines 292–328 requires a new relay plus independent mirror. [A:175](https://github.com/generalbusiness-ai/noseq/blob/2554c582db730cd3d64490970a573eab1463672e/notes/2026-09-06-noseq-architecture.md#L175).
Primary evidence: pinned [NIP-78:23](https://github.com/nostr-protocol/nips/blob/c3fd9af17939316bf6d0d83a5759100f8b0a1bdb/78.md#L23) recommends serving kinds 78/30078 only to the authenticated event author. That does not automatically permit participants to read sequencer-authored entries. [NIP-01](https://github.com/nostr-protocol/nips/blob/c3fd9af17939316bf6d0d83a5759100f8b0a1bdb/01.md) defines filter/timestamp/EOSE behavior, and [NIP-42](https://github.com/nostr-protocol/nips/blob/c3fd9af17939316bf6d0d83a5759100f8b0a1bdb/42.md) authenticates a relay connection rather than noseq membership.
Impact/scenario: mirror publication succeeds but group members cannot query it; a truncated historical response is mistaken for completeness; timestamp-based tip discovery misses an entry; after connection hibernation an old authenticated subscription retains inappropriate access.
Fix sketch: specify accepted kinds and exact EVENT/REQ/CLOSE/OK/EOSE/CLOSED/AUTH behavior, filter subset, errors, routing and both historical/live read policy. Use non-replacing retained entries, known-tip/predecessor-by-ID fetching, bounded pages and a fixed target prefix. Persist the last verified tip, reject rollback/forks, and separately report whether freshness is confirmed, stale or unknown. Mirror acknowledgement is an observed receipt, not perpetual retention: add verified readback/export checks and a replication coverage watermark with holes explicitly represented. A write-policy plugin alone is not evidence of private reads.
Gate: test real strfry with the chosen read boundary, duplicate/reordered deliveries, EOSE with missing history, filter limits, partial replication, mirror-only replay and stale tips.
Effort L; risk MED because a narrow profile can be isolated; confidence HIGH.

[DESIGN-08] P1 — Extend the journal transaction contract through alarms and operator restore.
Evidence: A §7 lines 258–270 correctly specifies atomic entry/retry/tip/outbox storage and async signing serialization; §8 lines 300–328 adds alarms and recovery without an operator-restore invariant. [A:263](https://github.com/generalbusiness-ai/noseq/blob/2554c582db730cd3d64490970a573eab1463672e/notes/2026-09-06-noseq-architecture.md#L263).
Primary evidence: Cloudflare [SQLite storage](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/#transactionsync) requires a synchronous callback for transactionSync; its documentation also exposes point-in-time restoration. [Alarms](https://developers.cloudflare.com/durable-objects/api/alarms/) gives one alarm per object and bounded automatic retries.
Impact/scenario: the journal commits but no future wakeup is durably scheduled, leaving the outbox stuck until another request arrives. More seriously, an operator restores an older database and resumes signing with the same sequencing key, producing a conflicting successor to a history clients already retained. Deferring automatic failover does not remove that restore hazard.
Fix sketch: write the precise storage/serialization design with unique sequence and submission constraints; make any asynchronous signing candidate revalidate its predecessor inside the append boundary, or use a bounded synchronous signing path. Keep mirror network I/O outside the append transaction. Couple pending outbox work to a recoverable alarm schedule and idempotent delivery results. Restored instances must remain read-only until they reconcile to the highest externally committed tip with all required journal/retry bytes; if that cannot be established, refuse new signing and require an explicit new-instance/handover decision.
Gate: crash after every persistent write boundary, concurrent signing, lost receipt, alarm exhaustion and stale-database restore.
Effort L; risk HIGH because mistakes create signed history forks; confidence HIGH.

[DESIGN-09] P2 — Give the combined DO a resource and hibernation budget.
Evidence: A §8 lines 292–304 says “bounded” relay/replication without concrete limits; §13 lines 516–517 asks for measurements. [A:300](https://github.com/generalbusiness-ai/noseq/blob/2554c582db730cd3d64490970a573eab1463672e/notes/2026-09-06-noseq-architecture.md#L300).
Primary evidence: Cloudflare [WebSockets](https://developers.cloudflare.com/durable-objects/best-practices/websockets/) requires explicit hibernation APIs and restoration of connection state; attachments are connection-lifetime state, not durable account state. Outbound connections do not hibernate. Cloudflare [limits](https://developers.cloudflare.com/durable-objects/platform/limits/) bound storage, requests and connections.
Impact/scenario: a few wide subscriptions, slow readers or a prolonged mirror outage exhaust memory/journal capacity; cached authentication/filter maps vanish or become stale on wake; retries occupy every activation and suppress ordinary reads.
Fix sketch: budget envelope bytes after encoding, journal retention/quota, pending outbox bytes and age, filters per connection, result-page bytes, CPU, connection count, send queues, dependency fetches and retry work per alarm. Persist/restore bounded subscription state and revalidate access; disconnect slow consumers and make them catch up from their verified frontier. Refuse new writes before acknowledged history would need silent eviction. Index supported lookups and consume SQL pages before awaited network work. Pin a Cloudflare compatibility date and demonstrate idle hibernation plus recovery from more failures than platform automatic retries.
Gate: bounded load/slow-consumer/outage tests before the shared deployment is considered operable.
Effort M–L; risk MED; confidence HIGH.

[DESIGN-10] P2 — Freeze the retained runtime and JSON-to-buffer boundary before broadening rendering.
Evidence: A §3 lines 104–124 promises immutable closure and bounded evaluation; §4 lines 143–153 explicitly exposes the safe-integer/Float32Array choice. [A:104](https://github.com/generalbusiness-ai/noseq/blob/2554c582db730cd3d64490970a573eab1463672e/notes/2026-09-06-noseq-architecture.md#L104).
Lineage evidence: pinned atseq [runtime-profile.md](https://github.com/generalbusiness-ai/atseq/blob/6477b73f3be27880fd592f7015b4c7dcb1eda74a/docs/runtime-profile.md) and [Folder:47–86](https://github.com/generalbusiness-ai/atseq/blob/6477b73f3be27880fd592f7015b4c7dcb1eda74a/src/runtime/folder.ts#L47) provide concrete bounds, failure semantics and atomic projection persistence, rather than a requirement to copy its transport.
Impact/scenario: unavailable old sources prevent replay; a newly loaded definition expands into an oversized view or leaks plaintext through asset/network references; browser-dependent numeric behavior changes semantic state; transferring a typed array detaches data still owned by a projection.
Fix sketch: start with fixed definitions and a content-identified safe-integer JSON/JSONata/Lexicon profile. Verify the complete manifest/schema/program/view/asset closure under aggregate count/depth/byte limits and retain it under the history policy. Execute in an isolated worker with semantic budgets plus an operational watchdog. Render only trusted primitives with allowed props and explicit signed actions; validate URLs/assets and never allow definition-supplied script, arbitrary SVG handlers or network callbacks. Use fixed-point canonical coordinates converted in a bounded presentation adapter to Float32Array; specify scale, rounding, buffer ownership/layout and compare canonical state and buffer bytes, not GPU pixels. True typed-buffer fold outputs require another reviewed profile.
Gate: missing dependencies, malicious/oversized definitions, worker failure and JSON-to-buffer boundary tests.
Effort L; risk MED with the fixed-profile scope; confidence HIGH.

[DESIGN-11] P2 — Establish reproducible integration gates before building the visible demo.
Evidence: A §12 lines 472–480 records documentation-only ecosystem review; §13 lines 500–523 lists broad outcomes but no toolchain, test commands, fixtures or milestone dependency order. The pinned repository has no runnable verification baseline. [A:477](https://github.com/generalbusiness-ai/noseq/blob/2554c582db730cd3d64490970a573eab1463672e/notes/2026-09-06-noseq-architecture.md#L477).
Primary evidence: pinned [marmot-ts README:6](https://github.com/marmot-protocol/marmot-ts/blob/2f60dbb27d284f617ad873ccda568c0f2f07aa79/README.md#L6) labels the library Alpha; [line 52](https://github.com/marmot-protocol/marmot-ts/blob/2f60dbb27d284f617ad873ccda568c0f2f07aa79/README.md#L52) says full interoperability needs raw BIP-340 account-proof signing beyond the Applesauce EventSigner. [Applesauce models](https://applesauce.build/core/models.html#custom-models) can expose arbitrary values but do not supply a deterministic replay engine.
Impact/scenario: a successful two-browser board demonstration hides an unsupported signer path, absent persistence capability or arrival-order-dependent crypto behavior; later recovery work forces a protocol rewrite.
Fix sketch: the plan should pin package versions/source commits, runtime versions, lockfile and compatibility date, then establish one command each for static checks, deterministic vectors, state-machine faults, real relay/DO integration and browser acceptance. Use a local software signer first; make NIP-07/NIP-46/passkey paths capability-tested additions rather than unconditional promises. Require a cold offline restore, actual independent-mirror readback, and a no-provider-plaintext inspection before a demo can pass. No dependency install, tests or security audit were run in this design review because no noseq package/runtime exists.
Gate: every implementation milestone needs its inputs, allowed files, commands, expected evidence and STOP conditions; cryptocurrency/crypto-library marketing is not acceptance evidence.
Effort M for baseline, L for full integration evidence; risk LOW for establishing it; confidence HIGH.

Grounded direction recommendation

[DIRECTION-01] P2 — Use the second application to test the host boundary, not merely reskin the board.
Evidence: A §1 lines 48–51 and §13 lines 484–488 require new behavior as retained content. [A:484](https://github.com/generalbusiness-ai/noseq/blob/2554c582db730cd3d64490970a573eab1463672e/notes/2026-09-06-noseq-architecture.md#L484).
User value: a second unrelated definition, such as a small request/approval register with different action/state schemas, demonstrates that authors can build useful applications without a server or client rebuild. Load it into the already-running binary using the same allowlisted renderer primitives and a generic typed agent adapter.
Fix sketch: make the acceptance test compare host/client build hashes and server deployment identity before and after loading the second bundle; fail if app names or schema IDs trigger host code branches. Test two independent instances to ensure definitions, state, subscriptions and crypto material stay separate. This is evidence for the stated framework goal, not an extra product feature.
Effort M after the generic runtime; risk LOW; confidence HIGH that it is grounded in the stated aim.

Recommended decision set and dependency order

1. Before protocol implementation, choose the first confidentiality profile and adversaries: plaintext is confidential from provider/relays; explicitly list permitted public metadata, trusted client-host/update origin, malicious/removed-member behavior, archive recipients and the protection actually promised for stored history. A same-operator browser host still executes with plaintext/key access; encryption does not make its delivered JavaScript untrusted.
2. Run DESIGN-01/02/03/06 as bounded crypto/order/history feasibility gates. The stop result is legitimate if pinned Marmot cannot meet the chosen contract. Do not silently switch to pairwise NIP-44 or erase replay guarantees to make the demo pass.
3. Close DESIGN-04/05 into a minimal online-inviter authority and device protocol. Decide the history offered to new members and devices before creating accounts.
4. Fix the wire and retained runtime, then build independent verification/fold vectors. Implement the sequencer transaction and relay surface only against those contracts; exercise DESIGN-07/08/09 fault cases before UI integration.
5. Integrate the generic host, direct JSON rendering and fixed-point buffer adapter; prove DIRECTION-01 and the full acceptance matrix. A minimal deployment is one generic static client, one routing Worker/DO class with per-instance SQLite, and one independently operated strfry mirror plus only the access boundary actually required by the metadata policy. Large blobs, separate D1, passkeys and extra signer integrations are optional until measurements or the chosen policy require them.
6. Defer automatic sequencer failover/provider migration, cross-instance transactions, per-copy revocation of shared signing keys, runtime migrations, arbitrary executable apps and native typed-buffer semantics. Deferring them must be enforced with explicit refusal, not left as accidental permissiveness.

Acceptance evidence the detailed plan must name

- Independent wire fixtures; same canonical state/outcomes/prefix under randomized duplicate/reordered delivery, two clients and restart.
- MLS competing commits/withdrawals, membership races and stale epochs; same noseq prefix cannot hide distinct crypto input sets.
- All durable crash boundaries: client send/crypto/archive/frontier, server journal/retry/outbox/alarm, receipt uncertainty and replay.
- Malformed opaque payload versus unavailable key/dependency; all stop/rejection distinctions visible and reproducible.
- Invitation expiry/reuse/substitution, inviter offline, another device, lost device, lost-all-devices and cache-only deletion.
- Revoked admission, inner/outer actor mismatch, private historical/live mirror access, retained-prefix holes, conflicting tips and stale provider restore.
- Real mirror outage longer than automatic retries, bounded queue/backpressure behavior, hibernation wake and independent export/readback.
- Retained-source substitution/missing closure, numeric boundary and worker limits; direct JSON and geometry projection with SQL absent.
- Two unrelated app bundles loaded without changing host binaries or per-app server code, plus instance isolation.
- Measured small-workload replay latency, memory/state, journal/outbox growth, subscription cost and rendering cost, with explicit workload sizes and thresholds chosen by the plan.

Ecosystem review and limits

Current primary sources support the draft's broad layering: [NIP-01](https://github.com/nostr-protocol/nips/blob/c3fd9af17939316bf6d0d83a5759100f8b0a1bdb/01.md), [NIP-78](https://github.com/nostr-protocol/nips/blob/c3fd9af17939316bf6d0d83a5759100f8b0a1bdb/78.md), [NIP-89](https://github.com/nostr-protocol/nips/blob/master/89.md), [NIP-44](https://github.com/nostr-protocol/nips/blob/master/44.md), [NIP-59](https://github.com/nostr-protocol/nips/blob/master/59.md), Cloudflare documentation, [strfry](https://github.com/hoytech/strfry), [Nosflare](https://github.com/Spl0itable/nosflare), [Nostrify](https://nostrify.dev/store/) and [NDK](https://github.com/nostr-dev-kit/ndk) provide components, not the noseq contract. [Blossom](https://github.com/hzrd149/blossom) supplies a blob protocol; choosing an R2 bucket still needs the protocol service. [Buzz architecture](https://github.com/block/buzz/blob/main/ARCHITECTURE.md), [Vector](https://github.com/VectorPrivacy/Vector) and [Webxdc](https://webxdc.org/docs/) are product precedents rather than proofs of noseq's bounded confidential replay. [WebAuthn PRF](https://w3c.github.io/webauthn/#prf-extension) is a capability to test in the selected browser/recovery path, not a Nostr signing mechanism.

The governing Marmot snapshot checked here is 4a2bc65f8db5866cec3b2a127dedb37818eaf207; marmot-ts is 2f60dbb27d284f617ad873ccda568c0f2f07aa79; NIPs are c3fd9af17939316bf6d0d83a5759100f8b0a1bdb. Exact source reads confirmed the quoted semantics after resolving those revisions. Marmot's current repository says its older MIP-era documents are deprecated, so new work should pin current surfaces rather than follow broken MIP links in library prose. These pins record evidence, not a tested compatible dependency set.

Considered and not reported as defects: public routing metadata is an explicitly acknowledged tradeoff; an opaque sequencer intentionally cannot enforce business schemas; a valid signature cannot guarantee freshness or availability; one writer/no automatic failover is a legitimate prototype scope; JSON-to-Float32Array presentation is explicitly allowed and should not force SQL or a schema migration. Those are choices to preserve and test.

Not audited: runtime code that does not yet exist; uncommitted plan files; performance or interoperability by executing candidate libraries; deployed infrastructure; the full implementation/security of Buzz, Vector, Marmot or Cloudflare; cryptographic proofs or library supply-chain audit. No source files, commits, merges, pushes, deployments, runtime changes or architecture adoption were made.
